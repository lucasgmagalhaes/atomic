# JS Runtime & Host — Capability Status

## 1. JavaScript runtime and host

**Done (92%)**

- [x] `Runtime`, `Context`, synchronous `eval` and exception conversion.
- [x] ES language execution through QuickJS-NG: classes, modules supported by the upstream runtime, promises, async functions, typed arrays, `Map`, `Set`, regex and standard built-ins.
- [x] Per-context DOM, storage and native-object state; per-runtime class registration.
- [x] Promise-job draining and host timer/event pumping.
- [x] Resource limits on selectors, DOM string inputs, event listeners, bubbling and nested dispatch.
- [x] `crypto.getRandomValues`.
- [x] `console` (`log`/`info`/`warn`/`error`/`debug`) with leveled message storage hosts can drain, and structured uncaught-error reporting (real exception text + a `window` `error` event).
- [x] Interrupt/time budget for untrusted script execution (`Context::set_time_budget`: quickjs's interrupt handler aborts a budget-exceeding `eval` with an "interrupted" InternalError; deadline re-stamped per call) and memory quotas per document (`Context::set_memory_limit`, quickjs's runtime-wide allocation cap — one runtime per context here, so per-document is exactly what it gives).

**Needed**

- [x] ES-module loader/resolver, import maps, dynamic `import()` and module cache. Stale line - loader/resolver/dynamic `import()`/module cache were already real and tested (`crates/js-runtime/src/module_loader.rs`'s `JS_SetModuleLoaderFunc`-backed `JSModuleNormalizeFunc`/`JSModuleLoaderFunc`, `context/eval.rs`'s `eval_module`: real compile→resolve→execute linking, a real module namespace, circular-dependency handling — `es_modules_test.rs`/`module_loader_test.rs`) before this line was last touched. Import maps (the one genuine remaining gap) done now: `Context::set_import_map(base_url, json)` (`crates/js-runtime/src/import_map.rs`) parses a real `{"imports": {...}}` object via `JS_ParseJSON`/`JS_GetOwnPropertyNames`, resolving a bare specifier (exact match, else longest `"prefix/"` match) that previously couldn't resolve at all — `import_map_test.rs`. Scope cuts: no `scopes` (one flat `imports` map only), no "one map, must precede every module" enforcement (last `set_import_map` call wins).
- [x] Script loading modes: parser-blocking, `defer`, `async`, module scripts and CSP-aware loading. Partially stale: `defer` ordering and `type="module"` are both real (`profile-worker`'s `page_source/scripts.rs`/`page/load.rs`, see the ES-module line above) - this document previously claimed module scripts weren't wired in at all. CSP-aware script loading also real now: `page_source/csp.rs`'s `is_script_allowed` gates every external `<script src>` fetch against `script-src` (falling back to `default-src`), with every CSP policy (response headers + `<meta http-equiv>`) collected before `load_scripts` runs rather than after — `crates/profile/tests/csp_test.rs` (3 new tests: header block, meta block, control). Same matching rules `js_runtime::csp::is_connect_allowed` already had for `connect-src` (`*`/`'none'`/`'self'`/explicit origin or host); inline `<script>` content stays ungated (no nonce/hash support, matching `js_runtime::csp`'s own documented scope cut). Still genuinely `[ ]`: real concurrent `async` ordering (this worker fetches scripts one at a time on a single thread, so `async` runs as a synchronous non-deferred script - an honest projection, not a distinct code path).
- [ ] Source maps, debugger protocol and remaining structured error reporting (console + uncaught-error reporting are done — see section 1's Done list; `EvalError` now carries the real stringified exception instead of the old "script raised an exception" placeholder).
- [x] Worker runtime: `Worker`, `SharedWorker`, `MessageChannel`, structured clone and transferable objects. Following the prior correction (this line was wrongly marked `[x]` once already, for a *Rust-only* `crates/workers::Worker` with no JS-facing binding - see git history), a real JS-facing `Worker` now exists: `crates/js-runtime/src/worker_bindings.rs`'s `new Worker(scriptText)` global spawns a genuine OS thread (its own `JSRuntime`/`JSContext`, never touched cross-thread), with real `postMessage`/`onmessage`/`addEventListener("message")` on both sides and real structured clone via `storage::value::Value` + `value_bridge::js_to_storage_value`/`storage_value_to_js` (the same `Send`-safe wire shape `window_registry`'s cross-window `postMessage` already established) — `worker_test.rs` (5 tests: bidirectional postMessage, clone independence, `terminate()`, non-blocking async construction). `SharedWorker` now real too: `crates/js-runtime/src/shared_worker_bindings.rs`'s `new SharedWorker(scriptText)` reuses `Worker`'s OS-thread/structured-clone primitives plus a `(JSRuntime pointer, script text)`-keyed instance registry so every same-script caller shares one worker thread instead of spawning a new one; each caller gets its own `.port` (a real, cross-thread-capable port object distinct from `message_channel.rs`'s same-realm-only `MessagePort`), and the worker side gets a real `self.onconnect` firing with a `MessageEvent` whose `.ports[0]` is that connection's own port — `shared_worker_test.rs` (2 tests: real onconnect/port round trip, instance reuse across two same-script `new SharedWorker()` calls proven via shared module-level state). `MessageChannel`/`MessagePort` (`message_channel.rs`) and `Uint8Array` transferable objects (`uint8array_transfer_test.rs`) were already real and JS-facing. Scope cuts, deliberate: `scriptText` is literal source, not a fetched URL (same cut `crates/workers::Worker::spawn` already documents); no nested workers, no `importScripts`; no cross-thread Transferable objects yet (`message_channel.rs`'s `Uint8Array` transfer stays same-realm-only); no `Worker`/`SharedWorker` `onerror`/`"error"` event (an uncaught worker-side exception is logged to stderr and swallowed); a worker stuck outside its message-receive loop (e.g. a synchronous infinite loop) can't be forcibly killed - `Worker.terminate()`/context teardown join its OS thread, which only returns once that thread reaches its own recv() point; a `SharedWorker` instance has no cross-context close-tracking (its OS thread outlives every individual connecting `Context`, torn down only with the owning `JSRuntime`) and no `.port.close()` signal reaching the worker side.
