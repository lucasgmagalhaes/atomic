# Events & Input — Capability Status

## 3. Events and input

**Done (55%)**

- [x] Stable element identity across lookups.
- [x] Ordered listeners, listener removal, listener count cap and exception isolation.
- [x] Event construction and option flags.
- [x] Target phase and bounded bubbling; cancellation and propagation stop.
- [x] Native profile-worker dispatch for click, keyboard input, focus, blur, input and change.

**Needed**

- [x] Capturing phase, `once`, `passive`, `signal`, listener objects and full event path/composed semantics. Capturing/`once`/`passive`/`signal`/listener-objects were already real (`crates/js-runtime/src/events/listeners.rs`'s `read_listener_options`/`make_record`, `events/dispatch/phase.rs`'s real three-`Phase` — `Capture`/`Target`/`Bubble` — dispatch over the ancestor chain built once and walked both directions, `abort_controller`'s `track_listener`/`fire_abort` deregistering a listener on real signal abort). `Event.composed`/`.composedPath()` done (`crates/js-runtime/src/events/event_class.rs`): `composed` reflects the constructor option; `composedPath()` returns the real target→root `Node` chain populated by `dispatch::chain::run_phases` during an actual `Node`-tree dispatch. Scope cut: a "simple" (non-`Node`) target like `window`/`document` has no DOM tree to walk, so `composedPath()` is always `[]` there; `path` also stays populated after dispatch completes rather than clearing per the real "dispatch flag unset" rule — no consumer here needs that stricter behavior.
- [x] Event subclasses: ~~`MouseEvent`~~, ~~`PointerEvent`~~, ~~`KeyboardEvent`~~, ~~`InputEvent`~~, ~~`FocusEvent`~~, ~~`SubmitEvent`~~, ~~`CustomEvent`~~, ~~`WheelEvent`~~, ~~`TouchEvent`~~, ~~`DragEvent`~~ — `CustomEvent`/`KeyboardEvent`/`PointerEvent` done in an earlier pass (see "Next implementation order" item 4); `MouseEvent` (`screenX`/`screenY`/`clientX`/`clientY`/`ctrlKey`/`shiftKey`/`altKey`/`metaKey`/`button`/`buttons`/`relatedTarget`) and `FocusEvent` (`relatedTarget`) done (2026-08-25, `crates/js-runtime/src/event_subclasses.rs`), same pattern as the earlier three: plain own data properties on top of `events::create_event`'s base `Event` object, prototype chained onto `Event.prototype` so `instanceof Event` holds. `relatedTarget` is the first field on any of these subclasses that's a `Node` reference rather than a primitive — read via a new `read_value_option` helper (no coercion, defaults to `null`) and written with a new `set_value_prop` that transfers ownership of the already-duped `JSValue` straight into `JS_SetPropertyStr`, same convention `detail`'s object-valued handling in `custom_event_constructor` already used ad hoc. `InputEvent` (`data`/`inputType`/`isComposing`) done (2026-08-25, same file): `data` reuses `relatedTarget`'s `read_value_option`/`set_value_prop` pair since the real API allows `data` to be `null` (composition/deletion events carry no string), not a primitive-only field like `inputType`/`isComposing`. ~~`WheelEvent`~~ — done (2026-08-25, see "Next implementation order" item 11 for the full writeup): `deltaX`/`deltaY`/`deltaZ`/`deltaMode`/`clientX`/`clientY`. ~~`SubmitEvent`~~/~~`TouchEvent`~~/~~`DragEvent`~~ — done (`crates/js-runtime/src/event_subclasses/focus_submit_drag_touch.rs`): `SubmitEvent.submitter`; `DragEvent` inherits every `MouseEvent` field plus `dataTransfer`; `TouchEvent` carries `touches`/`targetTouches`/`changedTouches` (plain arrays, no live `TouchList`) and the four modifier-key flags — all `null`/empty by default when constructed without options, all real `instanceof Event` subclasses.
- [ ] Pointer capture, hover/enter/leave, double-click, context menu, drag-and-drop, clipboard events and IME/composition. Partial: real coordinate-driven hover/enter/leave done (`crates/profile/src/bin/profile_worker/input_commands/mouse_move.rs`'s `dispatch_mouse_move`, wired as the new `MOUSE_MOVE x y` host command, `Profile::mouse_move`): hit-tests via the same `Page::hit_test_at` `CLICK_AT` uses, updates `dom::Dom`'s existing (previously dead) `:hover` state (`hover.rs`'s `set_hovered`/`clear_hover`), and dispatches real bubbling `mouseover`/`mouseout` plus non-bubbling `mouseenter`/`mouseleave` `MouseEvent`s. `mouseover`/`mouseout` fire on the nearest id-addressable ancestor *element* — anchored there rather than the raw hit-tested leaf specifically so a listener that mutates its own `textContent` (destroying the hit text node) doesn't wrongly read as "nothing hovered" on the next move. `mouseenter`/`mouseleave` fire on every id-addressable ancestor that entered/dropped out of the hover chain (`id_chain`'s real ancestor-*set* diff, not just the nearest node). Scope cut: `relatedTarget` stays `null` on all four (no binding yet for handing a live `NodeId` straight into a generated eval string). Real double-click also done (`click.rs`'s `dispatch_click_at`, extended): `WorkerState::last_click` tracks the previous `CLICK_AT` target id + `Instant`; a second click on the same id-addressable ancestor within 500ms dispatches a real bubbling, cancelable `"dblclick"` right after the second `"click"`, then resets (a third click starts a fresh sequence). Real context menu also done (`context_menu.rs`'s `dispatch_context_menu_at`, wired as `CONTEXT_MENU_AT x y`, `Profile::context_menu_at`): dispatches a real bubbling, cancelable `"contextmenu"` `MouseEvent` (`button: 2`) on the nearest id-addressable ancestor - no native menu exists in this engine to suppress, so the event itself is the real surface, and there's no focus side-effect (unlike `CLICK_AT`). Real clipboard events also done (`keyboard.rs`'s `dispatch_copy_or_cut`/`dispatch_paste`, recognized as `KEY "Ctrl+C"`/`"Ctrl+X"`/`"Ctrl+V"`): dispatches a real cancelable plain `Event` with a working `.clipboardData` (`getData`/`setData` closures built inline in the generated script), wired to the real OS clipboard via `platform_apis::clipboard_write_text`/`clipboard_read_text` (same primitive `navigator.clipboard` already uses, called synchronously since `KEY`'s round trip has no Promise-await path). Real default actions when not canceled: `copy`/`cut` copy the whole focused field's value (no partial-selection copy) unless the listener calls `setData` itself; `cut` also clears the field; `paste` appends the real clipboard text. Real pointer capture also done (`dom_bindings/pointer_capture.rs`, backed by `dom::Dom::set_pointer_capture`/`release_pointer_capture`/`has_pointer_capture`): real `setPointerCapture`/`releasePointerCapture`/`hasPointerCapture` on `Node.prototype`, firing real `"gotpointercapture"`/`"lostpointercapture"` events. Scope cut: this engine dispatches no real host-driven `PointerEvent`s at all yet (`MOUSE_MOVE`'s own real dispatch is `mouseover`/`mouseout`/`mouseenter`/`mouseleave`, not pointer events), so capture has nothing to redirect *to* - what's real is the bookkeeping API and its events. Real IME/composition also done (`event_subclasses/composition.rs`'s `CompositionEvent` - `.data` field, chained onto `Event.prototype`; `input_commands/composition.rs`'s `dispatch_composition_start`/`update`/`end`, wired as `COMPOSITION_START`/`COMPOSITION_UPDATE <text>`/`COMPOSITION_END <text>`, `Profile::composition_start`/`composition_update`/`composition_end`): `compositionstart` (cancelable) and `compositionupdate` (not cancelable, no field mutation - real IME preview-only) dispatch on whichever id was last focused; `compositionend` (not cancelable, matches real spec's "can't be prevented") always runs its default action afterward - appends the composed text to the field's `.value`, which itself already fires a real generic `"input"` event (`text_value.rs`'s `node_value_set`, same mechanism regular typed characters already use - no redundant second `InputEvent` built on top). Still `[ ]`: drag-and-drop (the one remaining sub-item).
