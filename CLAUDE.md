## Project naming — unresolved inconsistency

The project is referred to by **three different names** across the repo, not yet unified:

- `README.md` title: **idleGo**
- `mockup/browser-idle-spec.md` title: **IdleBrowser**
- `mockup/Nimble Browser.dc.html` (product mockup) branding: **Nimble**
- `mockup/github.md` refers to a file named "Idle Labs Browser.dc.html", which does not match the actual `Nimble Browser.dc.html` in the repo (flagged AMBIGUOUS by graphify — confidence 0.25, likely stale doc)

Do not assume one name is canonical. If you need to pick one for new code/docs, ask the user first — this has not been decided.

## Source of truth for architecture

`mockup/browser-idle-spec.md` is the technical execution spec (Rust workspace, crate breakdown, phased roadmap). `mockup/Nimble Browser.dc.html` is the UI/UX mockup (interactive HTML prototype) — it drives product features, not implementation.

The spec has a **"Features do mockup (UI) — mapeamento pra spec"** section that cross-references every mockup feature against the spec/roadmap. Known gaps not yet covered by any crate/phase as of the last review:

- Automation scripting (user-defined JS: `pane.goto/fill/click`, `every()`, `on()`, cron triggers) — no crate owns this; closest candidates are `workers`/`js-runtime` but neither specs it out
- Resource monitor (per-profile CPU/RAM/FPS telemetry + UI)
- Workspaces (named groups of profiles) — directory scaffolded (`apps/shell/src/workspace`) but no functional spec
- Downloads & history UI per profile
- Interface i18n (EN/PT toggle)
- "Import from Chrome" onboarding flow — conflicts with the "no fingerprint spoofing" isolation requirement, needs a decision
- Settings: Performance throttling knobs, credential vault UX, dev tools panel

Two prior conflicts (proxy support, 5 vs 6 simultaneous accounts) were resolved in favor of the mockup — see Requisitos and the `net` crate row in the spec's crate table.

## Implementation status

- **Phase 1 (done)**: Cargo workspace scaffold at repo root (`apps/shell`, `xtask`, `crates/*`). Every crate is an empty compiling stub except `crates/dom`, which has a real arena-based DOM tree (generation-tagged `NodeId`, tested: create/append, reparent, remove + generation invalidation, subtree removal).
- **Phase 2 (in progress)**: `quickjs-sys` vendors QuickJS-ng v0.16.2 as a git submodule (`crates/js-runtime/quickjs-sys/vendor/quickjs-ng`) and compiles it via a `cc` build script; hand-written FFI bindings cover runtime/context lifecycle, `JS_Eval`, native-function registration (`JS_NewCFunction2` + context opaque data), and now custom classes (`JS_NewClassID`/`JS_NewClass`/`JS_NewObjectClass`/`JS_SetOpaque`/`JS_GetOpaque`) plus accessor properties (`JS_DefinePropertyGetSet` with `JS_CFUNC_GETTER`/`JS_CFUNC_SETTER` cprotos). `js-runtime` wraps it in a safe `Runtime`/`Context` with `eval() -> Result<String, EvalError>`. `dom` gained `find_by_id`/`text_content`/`set_text_content`, now exposed to JS via a real `Node` class (a boxed `dom::NodeId` as the object's opaque data, freed by a `JS_NewClass` finalizer) and a global `document.getElementById(id)` returning `Node` instances with a live `textContent` getter/setter on `Node.prototype` — see `crates/js-runtime/src/dom_bindings.rs`. The two placeholder globals this replaced (`__dom_get_text_by_id`/`__dom_set_text_by_id`) are gone. `performance.now()` is bound (per-process time origin — no document/navigation concept exists yet to give it a real per-document origin). `crypto.getRandomValues` is bound too, scoped to `Uint8Array` only, backed by `platform-apis::fill_random` (wraps the `getrandom` crate — OS CSPRNG). `document.visibilityState`/`document.hidden` are bound as static placeholders (always "visible"/false, since nothing tracks real pane focus yet — see `crates/js-runtime/src/page_visibility.rs`). `dom_bindings` and `page_visibility` share one `document` global via `crate::document::get_or_create()` (fixed after a merge had them clobbering each other). `Node.prototype` also has `addEventListener`/`removeEventListener`/`dispatchEvent` (`crates/js-runtime/src/events.rs`) — scoped to one listener per (node, type), and `dispatchEvent(type)` takes a plain string, not a real `Event` object. `setTimeout`/`setInterval`/`clearTimeout`/`clearInterval`/`requestAnimationFrame`/`cancelAnimationFrame` are now bound too (`crates/js-runtime/src/timers.rs`) — that closes every phase 2 roadmap item. There's still no real event loop (belongs with `profile`/`ipc`'s per-tab process, which doesn't run one yet), so this is a manual/cooperative pump: `Context::run_pending_timers()` must be called explicitly by the host for any due timer or queued animation-frame callback to fire — nothing fires on a real clock or vsync on its own. Callback `JSValue`s are ref-counted (`JS_DupValue`) into a thread-local registry keyed by the `JSContext` pointer (not stored on `Context` itself, to avoid needing an unsafe `Send`/`Sync` impl just to hold a `!Send` `JSValue` behind a static) and freed either when they fire (one-shot) or on `Context::drop` (whatever's still pending). A `cancelled` id set handles the one real edge case that needed it: a `setInterval` callback calling `clearInterval` on itself mid-fire, since the firing timer is removed from the live queue for the duration of its own call.
- **Phase 3 (in progress)**: `css` has a real tokenizer (`lexer.rs`, a practical CSS Syntax Module Level 3 subset — no `url()`, no unicode-range), a selector/declaration parser (`parser.rs`, descendant combinator only, no `>`/`+`/`~`/pseudo-classes/attribute selectors, declaration values kept as raw tokens), and selector matching + cascade ordering (`cascade.rs`). `layout-engine` now depends on `css`+`dom` and does 3 things: `style.rs` resolves cascaded declarations into a typed `ComputedStyle` (`display`/`width`/`height`/`margin`/`padding`, no inheritance, no flex/positioning properties yet); `tree.rs` builds a `LayoutBox` tree by walking a live `dom::Dom` (only `Element` nodes get boxes, `display:none` prunes the subtree, no inline text layout — that needs the text-shaping crate); `layout.rs` computes `Dimensions` (block formatting context: no inline flow, no floats, no `position`, no margin collapsing) and dispatches per-box to `flex.rs` when `display: flex` — single-line flex only (no wrap/order/align-self/gap/shorthand), row and column direction, `flex-grow`/`flex-shrink` distribution, `justify-content`, `align-items`; tested including nested flex-in-flex. `flex-basis: auto` falls back to width/height then `0` — no content-based sizing exists anywhere in this engine. `layout-engine` also has `background-color`/`background` (solid color only: named colors, `#rgb`/`#rrggbb` hex). `render` now does real GPU work: `display_list.rs` flattens a `LayoutBox` tree into paint-ordered `Rect`s (skips transparent boxes), `gpu.rs`'s `GpuRenderer` rasterizes them via `wgpu` 0.20 to an off-screen texture and reads pixels back (headless, no window/surface — tested by asserting actual readback pixel values against a real adapter on this machine). One draw call, solid-color quads, straight alpha blending, no borders/images/text/shadows/clipping. `webgl` implements `create_shader`/`create_program`/`draw_triangles` (mirroring `gl.compileShader`/`gl.linkProgram`/`gl.drawArrays(TRIANGLES)`) over `wgpu`, using naga's GLSL frontend for *real* shader compilation. It now accepts real GLSL ES 3.00 source (`#version 300/310/320 es`) — the actual WebGL2 shading language, not a stand-in. Fix was narrower than "swap frontends": naga's GLSL frontend hard-codes its accepted `#version` line to `440`/`450`/`460` `core` (confirmed by reading its parser source), but everything after that line — precision qualifiers, `in`/`out`, `layout(location=N)` — is already shared grammar between GLSL ES 3.00 and desktop core GLSL 4.50 in naga's own parser (it accepts `precision highp float;` unconditionally, not gated on profile). So `rewrite_glsl_es_version` (`crates/webgl/src/context.rs`) rewrites just that one directive line before handing source to naga — real unmodified ES source in, no caller-side changes needed; tested against real `#version 300/310/320 es` shaders with mandatory precision qualifiers, including a full compile→link→draw→readback round trip. Doesn't cover GLSL ES 1.00 (WebGL1's `attribute`/`varying` language — different enough grammar that a version-line rewrite alone can't bridge it) or any ES 3.x construct naga's own GLSL frontend doesn't implement (it's a subset of desktop GLSL, not a complete implementation). Headless texture + pixel readback, same pattern as `render::gpu`; no textures/uniforms/indices/framebuffers/VAOs/persistent bind state. `render` also has `Canvas2D` (`canvas.rs`): `fillRect`/`clearRect`/`getImageData` over a persistent accumulating texture (unlike `gpu.rs`'s one-shot render), starts fully transparent, `clearRect` uses a separate REPLACE-blend pipeline so it actually erases instead of no-op-blending transparent onto opaque. Solid-color rects only, no paths/strokes/text/images/gradients/transforms. That closes the spec's phase 3 roadmap line (CSS + Canvas 2D + WebGL) — all three real, all narrowly scoped.

Text rendering (previously "not started") is now real end to end: `layout-engine` gained `font-size`/`color` as its first *inherited* properties (`resolve_style` seeds from the parent's resolved value, not the CSS initial value), `dom::NodeData::Text` nodes produce a leaf `LayoutBox` (`text: Some(string)`) instead of being skipped, and `layout::layout_block` short-circuits text boxes to `layout_text_box`, which shapes/line-wraps via real `cosmic-text` (`text.rs`) against the containing width — actual line breaking, not a heuristic. `text.rs` also rasterizes glyphs to alpha-coverage bitmaps via `SwashCache` (`rasterize_glyph`), matching cosmic-text's own `PhysicalGlyph`/`with_pixels` convention. `render` composites them (`text.rs`'s `composite_glyphs`, CPU-side alpha blending, not a GPU glyph-atlas pipeline) onto the same pixel buffer `gpu`/`canvas` use, tested end to end from `dom` through to an actual non-transparent painted pixel. Real inline formatting context now too: `layout-engine::tree` groups consecutive text + `display: inline` element children into one synthetic inline box (`LayoutBox::inline_spans`, built by the new `collect_inline_spans`/`build_children`), shaped together as one paragraph by `text::layout_inline` — genuine multi-span `cosmic-text` shaping via `set_rich_text` and `Attrs::metadata` to recover each glyph's original span (and therefore its own color/font-size) after cosmic-text has merged everything into one wrapped layout, not string concatenation with uniform styling. `<p>hello <b>world</b></p>` now wraps "hello" and "world" together onto the same line(s), each keeping its own cascaded color — tested including nested inline elements (`<b>b <i>c</i> d</b>` flattens into one run) and a fast path that keeps the pre-existing plain-text-only case (no inline-element siblings) on the cheaper single-span `text: Some(...)` box unchanged. Not modeled: a block-level element appearing inside inline content (real browsers "de-inline" it via anonymous block splitting; this engine doesn't), and there's still no tag-based UA-stylesheet default — a stylesheet has to say `b, span { display: inline; }` explicitly for this to kick in at all.
- **Phase 4 (started)**: `ipc` has a real shared-memory double-buffered frame transport (`framebuffer.rs`, via the `shared_memory` crate) — one atomic `ready_index` picks which buffer is safe to read; the writer only ever writes the *other* one, so a reader can never observe a torn frame (resolves the spec's own "pendente: definir sincronização" note in favor of lock-free double buffering). `profile` spawns a real child OS process (`profile-worker` binary, `std::process::Command`) that hosts dom+css+js-runtime+layout-engine+render and publishes frames over that transport; `Profile` (host side) does `ping`/`reload`/`latest_frame`, and `quit()`+`Drop` guarantee a profile process is killed even if it hangs or the handle is dropped without `quit()` — the actual crash-isolation/security boundary, not just a logical one. `profile-worker` now runs a real fixed-cadence ~60Hz loop (`Instant`-scheduled, resyncing rather than queuing missed frames under load — a real vsync loop drops frames, it doesn't catch up) instead of rendering once and blocking on stdin: a dedicated thread reads `PING`/`RELOAD`/`QUIT` off stdin into a channel the render loop drains non-blockingly each tick, and every tick also pumps a `js_runtime::Context`'s timers (closing the loop `js-runtime`'s `timers` module needed — `setTimeout`/`setInterval`/`requestAnimationFrame` finally have a real per-frame caller, not just tests) and re-renders from whatever the JS-mutable DOM looks like now. `Context` gained a `dom()` accessor so the host can read back what JS just mutated. The worker's demo page now includes a counter paragraph a hardcoded demo script updates via `setTimeout`/`requestAnimationFrame` every reload, and `profile`'s tests assert on this end to end: frame generation keeps climbing with zero commands sent (proving the loop runs on its own), and two frames taken 300ms apart have different pixel bytes (proving the JS-driven DOM mutation is actually reaching the rasterizer, not just being accepted and ignored). `GpuRenderer` is created once and reused across every tick — recreating a GPU device every frame was the loop's real bottleneck during development, caught by a "frame generation never advances" test failure. `html` implements `html5ever::TreeSink` over `dom::Dom` (`sink.rs`, modeled on html5ever's own `examples/arena.rs`) — real tag-soup error recovery, implied tags, adjacent-text merging, all from html5ever's tree builder, not reimplemented. `elem_name()` needs a real `&'a QualName` that `dom::NodeData::Element`'s plain `tag: String` can't provide, so element `QualName`s live in an `elsa::FrozenMap` side table keyed by `NodeId` instead (sidesteps a `RefCell<HashMap>` lifetime problem — `elem_name`'s signature needs a reference borrowed from `&'a self`, which a `Ref<'_, HashMap<..>>` guard can't hand back). Scope cuts (documented in `sink.rs`), all because `dom` has no node variant for them: doctype is parsed but discarded, processing instructions become comment nodes, `<template>` "contents" isn't a real isolated fragment (just the template element itself), no MathML/SVG foreign-content handling. `profile-worker` now parses real HTML via `html::parse_to_html_element` instead of a hardcoded DOM tree — the HTML source is still a fixed demo string (`net` isn't wired in to fetch a URL) and there's no `<style>`/`<link>` extraction (stylesheet applied separately). No input/navigation commands yet either (stdin protocol is just `PING`/`RELOAD`/`QUIT`). `net` has a real HTTP/TLS GET client (`hyper`+`hyper-rustls`, `rustls`'s `ring` backend not the default `aws-lc-rs` — no `cmake`/`nasm` on this machine — synchronous facade over a single-use `tokio` runtime per call, tested against a real HTTPS request), scoped to one GET with no redirects/cookies/caching/pooling/proxy yet. `workers` implements Web Workers as real OS threads (`Worker::spawn`), each with its own `js_runtime::Runtime`/`Context` — genuine parallelism, not cooperative; a worker can only reply via its `onmessage(event)` handler's *return value* (no async `postMessage` from inside a handler — that needs a native binding in `js-runtime` that doesn't exist yet), messages are plain hand-escaped JS string literals, not structured clone. `storage` has `localStorage`/`sessionStorage`-shaped persistence (`LocalStorage`, one newline-delimited file per origin, flushes every mutation), real cookies (`storage::cookies`: `Set-Cookie` parsing including `Max-Age`/a hand-rolled RFC 1123 `Expires` date parser — no external date crate, just the standard days-since-epoch civil-calendar algorithm — real domain/path/secure matching per RFC 6265 §5.1.3/5.1.4, a persisted `CookieJar`; no `SameSite` enforcement or public-suffix-list-aware domain checks), and a scoped-down IndexedDB (`storage::indexed_db`: multiple real persisted object stores per database plus one secondary index per store, built directly on `LocalStorage`'s own file format — no versioned schema/`onupgradeneeded`, no async transactions). Values are real structured-clone-shaped trees now (`storage::value::Value`: null/bool/number/string/array/object), not opaque strings — a hand-rolled recursive-descent JSON-like parser/encoder (`Value::parse`/`to_wire`, no serde, same convention as `css`'s hand-rolled lexer) is the on-disk wire format; `clone_deep` is real (tested: mutating a fetched value never touches what's stored) since every `Value` is already an owned, unaliased tree, so an ordinary `.clone()` *is* a structured clone. No `Date`/`Map`/`Set`/`ArrayBuffer`/circular refs. `ObjectStore::open_cursor` gives real ordered iteration (`Cursor`, sorted lexicographically, `Next`/`Prev`) over a store's primary keys, optionally bounded by a `KeyRange` (`only`/`lower_bound`/`upper_bound`/`bound`, open or closed) — deliberately not a standard Rust `Iterator`, matching `IDBCursor`'s real "starts before the first entry, `advance()` moves to it" protocol instead of hiding it behind `next()`. Cursors only walk a store's primary keys, not an index's (`get_by_index` remains the eager way to query one); index values still must be supplied explicitly by the caller rather than derived from a `keyPath`. `net::Response` now carries every response header (`headers: Vec<(String, String)>`, multi-valued `Set-Cookie` included as separate entries) and `net::get_with_headers` can attach request headers (e.g. a `Cookie` header built from a jar) — `net` itself still owns no cookie policy, that's `storage::cookies`' job. `security` has real AES-256-GCM on-disk encryption (`encrypt`/`decrypt`/`generate_key`, randomness from `platform_apis::fill_random` — the same source `crypto.getRandomValues` uses) — wrong-key and tampered-ciphertext both fail authentication (tested). It also has real Windows process sandboxing now (`security::sandbox`, `crates/security/src/sandbox/windows_job.rs`): a Job Object per profile process with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` + a hard active-process cap (1) + a hard total-memory cap, tested against a real spawned `powershell` process on this machine — one test round-trips the limits via `QueryInformationJobObject` to prove they were actually programmed, the other confirms the OS itself kills a still-running confined process the moment the job handle closes (checked independently via `tasklist`, not just our own `Child::try_wait`). `profile::Profile::spawn` now calls `security::sandbox::confine` on every spawned `profile-worker`, holding the `Sandbox` guard for the process's lifetime; a real confinement failure is fatal on Windows (the process would otherwise run unconfined), but `Err(Unsupported)` isn't, since Linux (seccomp + PID/mount/network namespaces via `unshare`/`clone`) and macOS (`sandbox_init` SBPL profiles, or the App Sandbox entitlement model) are real, different primitives that need a Linux/macOS machine to build and test against — `security::sandbox::confine` is a documented no-op there rather than a fake implementation. `security` also has a real signed updater now (`security::updater`): `ed25519-dalek` signs a small manifest (`version` + SHA-256 of the artifact, real `sha2` streamed hashing, not loaded whole into memory), `apply_update` verifies the manifest's signature, then re-hashes the artifact and checks it against the (now-trusted) manifest before an atomic `fs::rename` swaps it into place — tested against wrong-key, tampered-manifest, and swapped-artifact-after-signing cases, all rejected, `install_path` left untouched in every failure case. This checks *what update fed the binary*, not the binary's own OS-level signature (Windows Authenticode / macOS notarization — needs a CA-issued certificate this project doesn't have, and is a separate, orthogonal mechanism from what's implemented here). No update feed (fetching/parsing a remote manifest — policy layer on top of `net`, not this crate's job), no delta patching, no rollback-on-failed-launch. `platform-apis` also has real OS clipboard read/write (`arboard`, text only). `apps/shell` has `WorkspaceManager` (named profile groups, create/switch/move — closes the "workspaces" mockup gap) as a real tested data layer, and the GUI is wired to the real render stack now (`apps/shell/src/browser_view.rs`): `BrowserView::spawn` locates the sibling `profile-worker` binary next to the running executable (`worker_binary_path`, tested against the real build output) and spawns a real `profile::Profile`; every `eframe::App::update` tick polls `Profile::frame_generation()`/`latest_frame()` and uploads a changed frame as an `egui::TextureHandle` (`rgba_to_color_image`, also directly tested) — the window is genuinely displaying whatever `profile-worker`'s own real vsync loop just rendered, not a placeholder. Verified by actually running `shell.exe`: both it and the spawned `profile-worker` stayed alive and consumed real CPU (the vsync loop working) with zero stderr output over several seconds. Still scoped down from real browser chrome: one fixed-size profile, no tabs/workspaces UI wiring (`WorkspaceManager` remains data-layer-only), no window-resize-driven re-spawn, "Reload" is the only control (no address bar — `net` isn't wired to accept a URL from `profile-worker` yet either). `js-runtime` now has real `document.cookie` and `indexedDB` access too: `Context::with_storage(runtime, dom, host, storage_dir)` (alongside the existing `new`/`with_dom`) wires a real `storage::cookies::CookieJar` and a base directory for `indexedDB.open`, both behind a new `HostState` struct that replaced the old bare-`dom::Dom` opaque-pointer payload (`dom_bindings`'s `dom_opaque` now takes a raw pointer to `HostState.dom` via `addr_of_mut!` instead of casting the whole opaque slot). `document.cookie`'s getter/setter (`document_cookie.rs`) round-trips through the exact same `storage::cookies::parse_set_cookie`/`CookieJar::header_value` an HTTP `Set-Cookie` header would use — `document.cookie = "a=1; Max-Age=3600"` is real Set-Cookie grammar, not a separate ad-hoc parser. `indexedDB.open(name)` (`indexed_db_bindings.rs`) returns a real `IDBDatabaseHandle`-shaped JS object (a custom class wrapping a boxed `storage::indexed_db::IndexedDb`, one per open call — real multi-database-per-origin, not a single global db) with `createObjectStore`/`put`/`get`/`delete`/`clear`; values cross the JS↔Rust boundary as genuine structured-clone trees via the new `value_bridge` module (`js_to_storage_value`/`storage_value_to_js`), which needed extending `quickjs-sys` with real property-enumeration FFI (`JS_GetOwnPropertyNames`/`JS_FreePropertyEnum`/`JS_AtomToCStringLen`, plus `JS_IsArray`/`JS_GetLength`/`JS_GetPropertyUint32`/`JS_SetPropertyUint32`/`JS_NewArray`) — a JS object passed to `put` becomes a real `storage::value::Value` tree by walking its own enumerable properties, not a `JSON.stringify` round trip (tested: a full object with nested array/bool/null fields round-trips through `put`/`get` with real field values, not a stringified blob). Both bindings are always globally present (registered in `Context::new` itself) but stay inert without `with_storage` — `document.cookie` reads `""`, `indexedDB.open` returns `null` — rather than requiring every `Context` to opt in just to avoid a missing-global error. No cursors/indexes exposed to JS yet (`storage::indexed_db` has real ones, `Cursor`/`KeyRange`/`get_by_index`, just not wired to a binding in this pass), no `IDBOpenDBRequest`/versioned-schema/transaction model (synchronous CRUD only, same "no event loop yet" deviation as `fetchSync`/`timers`), and cookies have no per-document URL/path tracking (`path` is always `/`, `secure` is always treated as true).

`js-runtime` now has `fetchSync(url)`, a real network call (`net::get`, real HTTPS request, tested both with a mocked bad-URL case and against a live `https://example.com` in an ignored test) exposed to JS as `{ ok, status, body }` — synchronous, not `Promise`-based, since there's still no event loop/microtask queue (same gap blocking timers/rAF, deferred to phase 4's `profile` process); binary responses are lossily UTF-8-decoded since there's no `ArrayBuffer`/`Uint8Array` return path yet. Real async `fetch()` and `XMLHttpRequest` exist now too (`fetch_async.rs`), alongside `fetchSync` rather than replacing it: `fetch(url)` returns a genuine `Promise` (`JS_NewPromiseCapability`), backed by a real OS thread doing the blocking `net::get` (same "real parallelism" approach `workers` already uses), resolved/rejected by `Context::run_pending_timers` — which is now `timers::pump` plus `fetch_async::pump` plus a loop over `JS_ExecutePendingJob` to actually run `.then()`/`await` continuations once something resolves. `new XMLHttpRequest()` uses a hand-built native constructor (`JS_CFUNC_CONSTRUCTOR_OR_FUNC` — quickjs doesn't pre-allocate the instance for a plain C constructor, so it builds the object and links its prototype itself via the newly-bound `JS_SetPrototype`) with `open`/`send`/`onload`/`onerror`/`readyState`/`status`/`responseText`. Tested against real network requests (`example.com`) including a genuine `async () => { await fetch(...) }` completing through the pump loop. Building this surfaced a real reference-counting bug worth remembering: `JS_Call`'s `argv` is `JSValueConst*` (borrowed), not consumed — passing an owned `JSValue` as an argument and forgetting to free it afterward leaks it, caught by quickjs's own `list_empty(&rt->gc_obj_list)` debug assertion firing on `JS_FreeRuntime` in a test run, not silently. No `addEventListener("load", ...)` form for XHR (only assignable `onload`/`onerror` properties), no request bodies/headers on either API, no `AbortController`.

## Conventions

- Commits: Conventional Commits, one crate/domain per commit (`feat(dom): ...`, `chore(scaffold): ...`, `docs: ...`).
- All code, docs, and commit messages: English.
- Never commit `graphify-out/` (gitignored — contains absolute local filesystem paths).
- Tests are integration-style, not inline `#[cfg(test)] mod tests` in `src/`: put them under `crate/tests/<file>_test.rs` (e.g. `crates/dom/tests/dom_test.rs`). Only works cleanly when the tests exercise the crate's public API — if a test needs a private item, that's a signal to reconsider what's private, not to fall back to an inline module.
