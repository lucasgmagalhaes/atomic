**Needed**

- [x] CSSOM: `CSSStyleSheet`, `CSSStyleDeclaration`, `getComputedStyle`, `style`, stylesheet mutation and adopted stylesheets. Stale line - already fully real, not a gap: `getComputedStyle(element)` (`crates/js-runtime/src/computed_style.rs`) is a real global returning a snapshot `CSSStyleDeclaration`-shaped object backed by `HostState.computed_styles`, which `profile-worker`'s `Page::render` pushes in wholesale after running `layout-engine`'s real cascade resolver - documented deviation: a point-in-time snapshot, not a live view (calling it again after a mutation + re-render gives an up-to-date answer, but the same returned object doesn't mutate in place). `element.style` (`crates/js-runtime/src/css_style/`) is a real `CSSStyleDeclaration` reflecting the inline `style` attribute both directions, with `setProperty`/`getPropertyValue`/`removeProperty`/`cssText`/named kebab-to-camel accessors for every property `layout-engine`'s cascade resolver understands. `CSSStyleSheet` (`crates/js-runtime/src/cssom_stylesheet.rs`) has real `insertRule`/`deleteRule`/`cssRules`/`document.adoptedStyleSheets`. All covered by real tests (`computed_style_test.rs`, `cssom_stylesheet_test.rs`).
- [ ] Incremental style/layout invalidation and retained layout tree (currently safe full relayout is used).
- [~] Full formatting contexts: multicolumn, ruby, replaced-element rules and fragmentation still `[ ]`. Table layout is real (2026-09-14, `crate::table`) — a real `display: table`/`table-row`/`table-cell` three-level box structure: column count is the widest row's own cell count, every column gets an equal `content_width / num_columns` share (no content-based intrinsic sizing - same "real but simplified" scope cut `grid.rs`'s own missing `minmax()` already takes), row height is the tallest cell in that row (measured via a real two-pass layout, same shape `grid.rs`'s own row-height pass already uses), and cells paint/hit-test individually via the normal `layout_block` recursion, so backgrounds/borders/text/nested elements inside a cell are all real. No `colspan`/`rowspan`, no anonymous box generation (a `<td>` needs an explicit `display: table-cell` from the page's own stylesheet, same "no tag→display default table" gap this engine's `display: inline` already has), no `border-collapse`, no distinct row-grouping level (`table-row-group`/`thead`/`tbody`/`tfoot` aren't modeled - every `display: table` child is treated as a row directly). List markers are real (2026-09-14) — `list-style-type` (`disc`/`circle`/`square`/`decimal`/`none`) and `list-style-position` (parsed, but no distinct visual effect - see below) as real CSS properties (`crates/layout-engine/src/style/`), with real per-`<ol>` ordinal counters that correctly nest (a nested `<ol>` inside an `<li>` restarts its own counter, since each gets its own independent `build()` call). Painted as a real Unicode glyph (`•`/`◦`/`▪`) or the item's ordinal text through the *existing* font-shaping pipeline (`crate::text`, `cosmic-text`) rather than a new paint primitive - `render` never has to know a marker isn't ordinary text. Scope cuts, both documented in `crates/layout-engine/src/style/types.rs`'s own `ListStyleType`/`ListStylePosition` docs: (1) `armenian`/`georgian`/custom `@counter-style` aren't modeled, and `<ol start>`/`<li value>` aren't read - the ordinal is always the item's 1-based position among its list's real `<li>` children; (2) `list-style-type` isn't a generically *inherited* property here (this crate only threads `font_size`/`color` through the whole recursive box-tree build) - the one real-world case that matters, `ol { list-style-type: ... }` styling every item at once, is covered directly (an `<li>` with no override falls back to its own `<ol>`/`<ul>` parent's resolved value), but a `list-style-type` set higher up the tree (e.g. on `body`) won't reach a list several ancestors below it; (3) `list-style-position: outside`/`inside` are both real, parsed values but paint identically - the marker is always merged directly onto the front of the `<li>`'s own first line (the only way to land it on the *same* line as the item's text with this crate's simple block-stacking layout, since a separate marker box would just stack above as its own row) - the real `outside`/`inside` distinction (hanging in the margin vs. counted as ordinary content) would need a margin-box concept or line-box narrowing this crate has neither of.
- [~] Full position model: real per-positioned-ancestor containing blocks (for `absolute`/`fixed`, both resolved against the page origin instead) still `[ ]`. `position: sticky` is real (2026-09-14) — scoped to a `top` inset relative to the whole page's own scroll (not a nested `overflow: scroll` container's - a documented cut, matching `profile-worker`'s own page-level scroll model). Needs **zero** layout changes (a sticky box stays in normal flow - its own `Dimensions::y` already is its real "natural" unstuck position); all the real behavior is paint-time, in `render`'s three display-list builders (tagging every primitive under a `Sticky` box with `(natural_y, top_px)`, the innermost sticky ancestor's own values winning over any outer one) plus `profile-worker`'s scroll shift, which computes `extra_shift = (top_px - (natural_y - scroll_top)).max(0.0)` and applies it uniformly to the whole tagged subtree - `0.0` (normal scrolling) before the sticky threshold is crossed, holding at `top_px` once it is, unsticking smoothly on scroll back up (recomputed fresh every frame, no stateful "is it stuck" flag). `bottom`/`left`/`right`-edge stickiness aren't modeled, and `top: auto` means a box just never engages sticky behavior. Tested at both layers (`render/tests/position_sticky_test.rs` for tag propagation, `profile/tests/scroll_behavior_test.rs` for a real end-to-end pixel test through actual scrolling) — note a sticky element still needs its own `z-index` to reliably paint above later, taller siblings without a stacking-context promotion, same as real CSS. Stacking contexts and z-index are real (2026-09-12) — `ComputedStyle::z_index`, `render::display_list`'s paint-order sort — see `spec/ROADMAP.md` items 24-25 for the exact scope cut. `transform` is real but 2D-translate-only (2026-09-12, `ROADMAP.md` item 26) — `rotate`/`scale`/`skew`/`matrix` parse but don't paint (no rotation/scale in this crate's paint primitives). `position: fixed` is real (2026-09-14) — `layout_engine::Position::Fixed` gets identical layout math to `Absolute` (both already resolve against the page's own origin, not a positioned ancestor, so there's no extra layout work) and is a real, paint-time-only difference: `render`'s three display-list builders (`Rect`/`ImageQuad`/`ClippedGlyph`) tag every primitive under a `Fixed` box (propagated down through descendants, same as `opacity`/`transform` already are), and `profile-worker`'s own page-scroll shift (`page/render.rs`) skips the `-scroll_top` shift for a tagged primitive — keeping it glued to the viewport while the rest of the page scrolls underneath. Tested at both layers: `layout-engine/tests/position_test.rs` (layout math) and `render/tests/position_fixed_test.rs` (tag propagation through the tree, including images/glyphs).
- [~] Fonts: `@font-face`, font loading API still `[ ]` (this engine fetches nothing over the network at box-tree/text-shaping time - a real, documented non-goal for the same reason `net`'s own gaps list has no redirect-following: no infrastructure exists yet to fetch/cache a font file mid-layout). Real `font-family` is done (2026-09-14) — a real, generically-*inherited* CSS property (`crates/layout-engine/src/style/types.rs`'s `FontFamily`/`GenericFontFamily`), scoped to the one real-world-common pattern: one specific name plus a trailing generic fallback (`font-family: Arial, sans-serif`) - not a full comma-separated fallback list, and no custom `@font-face`-registered names (only the 5 CSS generic keywords `cosmic-text`'s own `Family` enum already has a direct variant for). Inheritance is real down the whole box tree (a grandchild with no `font-family` rule of its own correctly picks up an ancestor's, tested in `font_family_test.rs`) but deliberately implemented one layer above `resolve_style`'s own public signature (`tree::snapshot::resolve_element_style`, not `resolve_style` itself) so the ~9 existing `*_style_test.rs` files that call `resolve_style` directly to test one property's cascade resolution in isolation didn't all need a new required parameter for a property none of them care about. Named-font matching is real system-font-database lookup via `cosmic-text`'s own `fontdb` (not a stub) - an installed font matching the name paints with it; one that isn't installed silently falls through to whatever `fontdb`'s own fallback finds. Shaping/kerning/line-breaking/bidi were already real via `cosmic-text` before this - what's newly real here is just *which* family gets requested, not the shaping pipeline itself.
- [~] CSS animations, transitions, filters, masks, blend modes and container queries still `[ ]`. `linear-gradient` backgrounds are real (2026-09-14) — 2-stop only (`from`/`to`, no percentage stop positions, no `radial-gradient`/`conic-gradient` - same "one value, not a list" scope cut `box-shadow` already has), real angle (`<deg>` or `to <side>[ <side>]` keywords, defaulting to the real spec default `to bottom`/`180deg`), parsed via both the `background`/`background-image` shorthand and longhand (`crates/layout-engine/src/style/apply_declaration.rs`). Painted with *zero new shader code* — `render::gpu::shader::rect_to_vertices` computes each of a gradient rect's 4 corners' own exact blend color (the real CSS gradient-line-length formula: the box's own half-diagonal projected onto the gradient direction) and lets the GPU's existing vertex-color interpolation do the rest; this is mathematically exact, not an approximation, for a 2-stop gradient (bilinear interpolation of an affine function from its 4 corner values reproduces that function exactly at every interior point). See `spec/matrix/paint.md`'s own entry for the render-side detail.
