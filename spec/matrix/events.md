## 3. Events and input

**Done (55%)**

- [x] Stable element identity across lookups.
- [x] Ordered listeners, listener removal, listener count cap and exception isolation.
- [x] Event construction and option flags.
- [x] Target phase and bounded bubbling; cancellation and propagation stop.
- [x] Native profile-worker dispatch for click, keyboard input, focus, blur, input and change.

**Needed**

- [x] Capturing phase, `once`, `passive`, `signal`, listener objects and full event path/composed semantics. Capturing/`once`/`passive`/`signal`/listener-objects were already real (`crates/js-runtime/src/events/listeners.rs`'s `read_listener_options`/`make_record`, `events/dispatch/phase.rs`'s real three-`Phase` — `Capture`/`Target`/`Bubble` — dispatch over the ancestor chain built once and walked both directions, `abort_controller`'s `track_listener`/`fire_abort` deregistering a listener on real signal abort). `Event.composed`/`.composedPath()` done (`crates/js-runtime/src/events/event_class.rs`): `composed` reflects the constructor option; `composedPath()` returns the real target→root `Node` chain populated by `dispatch::chain::run_phases` during an actual `Node`-tree dispatch. Scope cut: a "simple" (non-`Node`) target like `window`/`document` has no DOM tree to walk, so `composedPath()` is always `[]` there; `path` also stays populated after dispatch completes rather than clearing per the real "dispatch flag unset" rule — no consumer here needs that stricter behavior.
- [x] Event subclasses: ~~`MouseEvent`~~, ~~`PointerEvent`~~, ~~`KeyboardEvent`~~, ~~`InputEvent`~~, ~~`FocusEvent`~~, ~~`SubmitEvent`~~, ~~`CustomEvent`~~, ~~`WheelEvent`~~, ~~`TouchEvent`~~, ~~`DragEvent`~~ — `CustomEvent`/`KeyboardEvent`/`PointerEvent` done in an earlier pass (see "Next implementation order" item 4); `MouseEvent` (`screenX`/`screenY`/`clientX`/`clientY`/`ctrlKey`/`shiftKey`/`altKey`/`metaKey`/`button`/`buttons`/`relatedTarget`) and `FocusEvent` (`relatedTarget`) done (2026-08-25, `crates/js-runtime/src/event_subclasses.rs`), same pattern as the earlier three: plain own data properties on top of `events::create_event`'s base `Event` object, prototype chained onto `Event.prototype` so `instanceof Event` holds. `relatedTarget` is the first field on any of these subclasses that's a `Node` reference rather than a primitive — read via a new `read_value_option` helper (no coercion, defaults to `null`) and written with a new `set_value_prop` that transfers ownership of the already-duped `JSValue` straight into `JS_SetPropertyStr`, same convention `detail`'s object-valued handling in `custom_event_constructor` already used ad hoc. `InputEvent` (`data`/`inputType`/`isComposing`) done (2026-08-25, same file): `data` reuses `relatedTarget`'s `read_value_option`/`set_value_prop` pair since the real API allows `data` to be `null` (composition/deletion events carry no string), not a primitive-only field like `inputType`/`isComposing`. ~~`WheelEvent`~~ — done (2026-08-25, see "Next implementation order" item 11 for the full writeup): `deltaX`/`deltaY`/`deltaZ`/`deltaMode`/`clientX`/`clientY`. ~~`SubmitEvent`~~/~~`TouchEvent`~~/~~`DragEvent`~~ — done (`crates/js-runtime/src/event_subclasses/focus_submit_drag_touch.rs`): `SubmitEvent.submitter`; `DragEvent` inherits every `MouseEvent` field plus `dataTransfer`; `TouchEvent` carries `touches`/`targetTouches`/`changedTouches` (plain arrays, no live `TouchList`) and the four modifier-key flags — all `null`/empty by default when constructed without options, all real `instanceof Event` subclasses.
- [ ] Pointer capture, hover/enter/leave, double-click, context menu, drag-and-drop, clipboard events and IME/composition. Partial: real coordinate-driven hover/enter/leave done (`crates/profile/src/bin/profile_worker/input_commands/mouse_move.rs`'s `dispatch_mouse_move`, wired as the new `MOUSE_MOVE x y` host command, `Profile::mouse_move`): hit-tests via the same `Page::hit_test_at` `CLICK_AT` uses, updates `dom::Dom`'s existing (previously dead) `:hover` state (`hover.rs`'s `set_hovered`/`clear_hover`), and dispatches real bubbling `mouseover`/`mouseout` plus non-bubbling `mouseenter`/`mouseleave` `MouseEvent`s. `mouseover`/`mouseout` fire on the nearest id-addressable ancestor *element* — anchored there rather than the raw hit-tested leaf specifically so a listener that mutates its own `textContent` (destroying the hit text node) doesn't wrongly read as "nothing hovered" on the next move. `mouseenter`/`mouseleave` fire on every id-addressable ancestor that entered/dropped out of the hover chain (`id_chain`'s real ancestor-*set* diff, not just the nearest node). Scope cut: `relatedTarget` stays `null` on all four (no binding yet for handing a live `NodeId` straight into a generated eval string).
