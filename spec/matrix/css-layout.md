- [~] Full formatting contexts: ruby, replaced-element rules and fragmentation still `[ ]`. Multicolumn is real (2026-09-14, `crate::columns`) — real `column-count` on any block container (not a `display` keyword, unlike grid/table/flex, so checked independently), splitting children into `N` count-based chunks (`children.len().div_ceil(N)` per column, not real height balancing - the same "real but simplified" scope cut this pass's own table-layout already takes for column widths), each stacked vertically within its own equal-width column. No `column-width`/`columns` shorthand/`column-gap`/`column-rule`/`column-span`, no cross-column element fragmentation. Table layout is real (2026-09-14, `crate::table`) — a real `display: table`/`table-row`/`table-cell` three-level box structure: column count is the widest row's own cell count, every column gets an equal `content_width / num_columns` share (no content-based intrinsic sizing - same "real but simplified" scope cut `grid.rs`'s own missing `minmax()` already takes), row height is the tallest cell in that row (measured via a real two-pass layout, same shape `grid.rs`'s own row-height pass already uses), and cells paint/hit-test individually via the normal `layout_block` recursion, so backgrounds/borders/text/nested elements inside a cell are all real. No `colspan`/`rowspan`, no anonymous box generation (a `<td>` needs an explicit `display: table-cell` from the page's own stylesheet, same "no tag→display default table" gap this engine's `display: inline` already has), no `border-collapse`, no distinct row-grouping level (`table-row-group`/`thead`/`tbody`/`tfoot` aren't modeled - every `display: table` child is treated as a row directly). List markers are real (2026-09-14) — `list-style-type` (`disc`/`circle`/`square`/`decimal`/`none`) and `list-style-position` (parsed, but no distinct visual effect - see below) as real CSS properties (`crates/layout-engine/src/style/`), with real per-`<ol>` ordinal counters that correctly nest (a nested `<ol>` inside an `<li>` restarts its own counter, since each gets its own independent `build()` call). Painted as a real Unicode glyph (`•`/`◦`/`▪`) or the item's ordinal text through the *existing* font-shaping pipeline (`crate::text`, `cosmic-text`) rather than a new paint primitive - `render` never has to know a marker isn't ordinary text. Scope cuts, both documented in `crates/layout-engine/src/style/types.rs`'s own `ListStyleType`/`ListStylePosition` docs: (1) `armenian`/`georgian`/custom `@counter-style` aren't modeled, and `<ol start>`/`<li value>` aren't read - the ordinal is always the item's 1-based position among its list's real `<li>` children; (2) `list-style-type` isn't a generically *inherited* property here (this crate only threads `font_size`/`color` through the whole recursive box-tree build) - the one real-world case that matters, `ol { list-style-type: ... }` styling every item at once, is covered directly (an `<li>` with no override falls back to its own `<ol>`/`<ul>` parent's resolved value), but a `list-style-type` set higher up the tree (e.g. on `body`) won't reach a list several ancestors below it; (3) `list-style-position: outside`/`inside` are both real, parsed values but paint identically - the marker is always merged directly onto the front of the `<li>`'s own first line (the only way to land it on the *same* line as the item's text with this crate's simple block-stacking layout, since a separate marker box would just stack above as its own row) - the real `outside`/`inside` distinction (hanging in the margin vs. counted as ordinary content) would need a margin-box concept or line-box narrowing this crate has neither of.
- [~] Full position model: real per-positioned-ancestor containing blocks (for `absolute`/`fixed`, both resolved against the page origin instead) still `[ ]`. `position: sticky` is real (2026-09-14) — scoped to a `top` inset relative to the whole page's own scroll (not a nested `overflow: scroll` container's - a documented cut, matching `profile-worker`'s own page-level scroll model). Needs **zero** layout changes (a sticky box stays in normal flow - its own `Dimensions::y` already is its real "natural" unstuck position); all the real behavior is paint-time, in `render`'s three display-list builders (tagging every primitive under a `Sticky` box with `(natural_y, top_px)`, the innermost sticky ancestor's own values winning over any outer one) plus `profile-worker`'s scroll shift, which computes `extra_shift = (top_px - (natural_y - scroll_top)).max(0.0)` and applies it uniformly to the whole tagged subtree - `0.0` (normal scrolling) before the sticky threshold is crossed, holding at `top_px` once it is, unsticking smoothly on scroll back up (recomputed fresh every frame, no stateful "is it stuck" flag). `bottom`/`left`/`right`-edge stickiness aren't modeled, and `top: auto` means a box just never engages sticky behavior. Tested at both layers (`render/tests/position_sticky_test.rs` for tag propagation, `profile/tests/scroll_behavior_test.rs` for a real end-to-end pixel test through actual scrolling) — note a sticky element still needs its own `z-index` to reliably paint above later, taller siblings without a stacking-context promotion, same as real CSS. Stacking contexts and z-index are real (2026-09-12) — `ComputedStyle::z_index`, `render::display_list`'s paint-order sort — see `spec/ROADMAP.md` items 24-25 for the exact scope cut. `transform` is real but 2D-translate-only (2026-09-12, `ROADMAP.md` item 26) — `rotate`/`scale`/`skew`/`matrix` parse but don't paint (no rotation/scale in this crate's paint primitives). `position: fixed` is real (2026-09-14) — `layout_engine::Position::Fixed` gets identical layout math to `Absolute` (both already resolve against the page's own origin, not a positioned ancestor, so there's no extra layout work) and is a real, paint-time-only difference: `render`'s three display-list builders (`Rect`/`ImageQuad`/`ClippedGlyph`) tag every primitive under a `Fixed` box (propagated down through descendants, same as `opacity`/`transform` already are), and `profile-worker`'s own page-scroll shift (`page/render.rs`) skips the `-scroll_top` shift for a tagged primitive — keeping it glued to the viewport while the rest of the page scrolls underneath. Tested at both layers: `layout-engine/tests/position_test.rs` (layout math) and `render/tests/position_fixed_test.rs` (tag propagation through the tree, including images/glyphs).
- [~] Fonts: the `FontFace`/`document.fonts` JS loading API still `[ ]` (no JS binding surface for it - see `spec/matrix/browser-apis.md` for that gap's own tracking). Real `@font-face` CSS parsing+fetching is done (2026-09-14) — the css crate parses `@font-face { font-family: ...; src: url(...); }` into `css::FontFaceRule` (same division of labor `@import`'s own `ImportRule` already has: this crate only recognizes/extracts, a caller with network access fetches), and `profile-worker`'s new `page_source::load_font_faces` (called once per page load, right after `build_stylesheet` — which now also merges `font_faces` across `@import`s, same as it already does for `rules`) fetches each face's `src` URL through the same per-load `ResourceCache` every other resource uses and hands the raw bytes to `layout_engine::register_font_face`, which loads them into `cosmic-text`'s one process-wide `fontdb::Database` via `db_mut().load_font_data` — the exact same database `family_for`'s `Family::Name(...)` lookup already queries for an installed system font, so a page's fetched `@font-face` font resolves through the identical lookup path from that point on. Scope cuts: only the first `src: url(...)` in a comma-separated fallback list is fetched (no `format()`/further fallbacks); no `font-weight`/`font-style`/`unicode-range` (this crate's `FontFamily` has no weight/style-variant concept); and `fontdb` matches a loaded font by the family name *embedded in the font file's own metadata*, not the page's arbitrarily-declared `font-family` string — there's no "register under this alias" API in `fontdb`'s basic loader, so this is silently correct only when those two names coincide, true for the overwhelming majority of real `@font-face` declarations (an author names the family after the font itself); a mismatch just falls through to `fontdb`'s own fallback, identical to today's existing "named font isn't installed" behavior. A failed/unresolvable fetch registers nothing rather than failing the page load, matching `load_images`'s own best-effort stance. Tested at the parser level (`css/tests/at_rules_test.rs`, 4 new tests), the registration level (`layout-engine/tests/font_family_test.rs`, a no-panic-on-garbage-bytes smoke test), and end-to-end (`profile/tests/font_face_test.rs`, 2 tests: a real network GET for the `src` URL, and a face reachable only through `@import`). Real `font-family` (name matching itself, not fetching) is done (2026-09-14) — a real, generically-*inherited* CSS property (`crates/layout-engine/src/style/types.rs`'s `FontFamily`/`GenericFontFamily`), scoped to the one real-world-common pattern: one specific name plus a trailing generic fallback (`font-family: Arial, sans-serif`) - not a full comma-separated fallback list, and no custom `@font-face`-registered names (only the 5 CSS generic keywords `cosmic-text`'s own `Family` enum already has a direct variant for). Inheritance is real down the whole box tree (a grandchild with no `font-family` rule of its own correctly picks up an ancestor's, tested in `font_family_test.rs`) but deliberately implemented one layer above `resolve_style`'s own public signature (`tree::snapshot::resolve_element_style`, not `resolve_style` itself) so the ~9 existing `*_style_test.rs` files that call `resolve_style` directly to test one property's cascade resolution in isolation didn't all need a new required parameter for a property none of them care about. Named-font matching is real system-font-database lookup via `cosmic-text`'s own `fontdb` (not a stub) - an installed font matching the name paints with it; one that isn't installed silently falls through to whatever `fontdb`'s own fallback finds. Shaping/kerning/line-breaking/bidi were already real via `cosmic-text` before this - what's newly real here is just *which* family gets requested, not the shaping pipeline itself.
- [~] CSS `@keyframes` animations, filters, masks, blend modes and container queries still `[ ]`. Real `transition`/`transition-property`/`transition-duration` (2026-09-14, `crate::transition`) — scoped to the two paint-time-only properties this crate already threads through `render`'s display-list builders per primitive: `opacity` and `transform` (translate only, same scope `transform`'s own doc already has). `width`/`height`/`color`/border/etc. transitions aren't modeled - they'd need layout itself to re-run every animation frame, not just the paint step. `transition-timing-function` is always linear (no `ease`/cubic-bezier curves) and `transition-delay` isn't modeled. `TransitionStates::apply` is a pure `(tree, now) -> mutated tree` step with no idea what a frame or render loop is - `profile-worker`'s `Page::render` is the one real caller, once per real paint, using its returned in-flight-node list to bypass both `PaintCache` and per-layer caching for whatever's still mid-animation (neither cache's key includes wall-clock time, so without this a transition would freeze on the first repainted frame). A transition only engages on a value *change* after an element's own first paint, matching real CSS (no animation on initial style application) - the first time a given `NodeId` is seen is this crate's only signal for "first paint". Real "interrupt and retarget": changing the target again mid-flight starts the new run from wherever the old one currently sat, not from a jump. Tested in `layout-engine/tests/transition_test.rs` (7 tests: first-paint settling, linear interpolation, retargeting, zero-duration no-op, `transform`-only, `all`, and independent per-child animation). `linear-gradient` backgrounds are real (2026-09-14) — 2-stop only (`from`/`to`, no percentage stop positions, no `radial-gradient`/`conic-gradient` - same "one value, not a list" scope cut `box-shadow` already has), real angle (`<deg>` or `to <side>[ <side>]` keywords, defaulting to the real spec default `to bottom`/`180deg`), parsed via both the `background`/`background-image` shorthand and longhand (`crates/layout-engine/src/style/apply_declaration.rs`). Painted with *zero new shader code* — `render::gpu::shader::rect_to_vertices` computes each of a gradient rect's 4 corners' own exact blend color (the real CSS gradient-line-length formula: the box's own half-diagonal projected onto the gradient direction) and lets the GPU's existing vertex-color interpolation do the rest; this is mathematically exact, not an approximation, for a 2-stop gradient (bilinear interpolation of an affine function from its 4 corner values reproduces that function exactly at every interior point). See `spec/matrix/paint.md`'s own entry for the render-side detail.
