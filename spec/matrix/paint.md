# Paint, Canvas & Compositing — Capability Status

## 5. Paint, canvas and compositing

**Done (88%)**

- [x] GPU background/border rectangle pass.
- [x] CPU glyph rasterization/compositing and decoded image compositing.
- [x] Scroll-offset paint, clip regions, display lists and shared-memory frame publication.
- [x] Real `HTMLCanvasElement.getContext('2d')` JS wiring (2026-09-14) — the `render::Canvas2D` scaffold (`fillRect`/`clearRect`/`fillStyle`) is now actually reachable from page JavaScript (`js-runtime`'s new `canvas_bindings` module), not just a Rust-only orphan. `getContext(id)` only recognizes `"2d"`; the returned `CanvasRenderingContext2D` has just those three real members. Real per-canvas persistence: the backing `Canvas2D` lives in `HostState::canvases`, keyed by the canvas element's own `NodeId`, so drawn pixels/`fillStyle` survive across separate `getContext('2d')` calls on the same element — the one real spec deviation is that each call still returns a *new* JS wrapper object (`===` across two calls is `false`), since this crate has no per-`(ctx, NodeId)` cached-`JSValue` registry for this yet (the pattern `class_list`/`dataset`/`css_style` already use elsewhere would be the natural next step). `fillStyle` only parses/formats `#rgb`/`#rrggbb` hex (no `rgb()`/`hsl()`/named keywords — neither `render::Canvas2D` nor any publicly exposed `layout_engine` API had a general CSS-color-string parser to reuse). Real page compositing: `profile-worker`'s `Page::render` reads every active canvas's current pixels fresh every frame (`Context::canvas_snapshots`) and feeds them into a new `layout_engine::apply_canvas_snapshots`, which reuses the *existing*, already-tested `<img>` compositing pipeline (`render::build_image_list`/`composite_images`) — a canvas paints like any other replaced element, no new paint primitive. A canvas's own `width`/`height` HTML attributes (default `300`/`150`) size only its backing pixel buffer, read once at the first `getContext('2d')` call — not its layout box size, which ordinary CSS (or this crate's own block-level Auto-stretch default) always decides; a page wanting a specific on-screen size still needs real CSS `width`/`height`. Since this engine has no cheap way to detect whether a canvas's drawn content actually changed since the last frame, a page with any active 2D canvas context bypasses `PaintCache`/per-layer caching on *every* frame while that canvas exists (same shape this pass's CSS-transitions work already introduced for `TransitionStates`). Tested at three levels: `js-runtime/tests/canvas_test.rs` (7 tests: real context object, unsupported `contextId` returns `null`, hex `fillStyle` round-trip incl. 3-digit expansion, shared backing across repeated `getContext` calls), `layout-engine/tests/canvas_snapshot_test.rs` (5 tests), and `profile/tests/canvas2d_test.rs` (2 real end-to-end pixel tests through `Profile::spawn` + navigate + `latest_frame()`).
- [x] `linear-gradient` background paint (2026-09-14) — real per-vertex GPU color interpolation for a 2-stop `background`/`background-image: linear-gradient(...)` (`render::gpu::shader::rect_to_vertices`), mathematically exact for the 2-stop case, no new shader code. See `spec/matrix/css-layout.md`'s own entry for the CSS-parsing side. `radial-gradient`/`conic-gradient` and `Canvas2D`'s own separate gradient API (`createLinearGradient`/`createRadialGradient`) are still `[ ]` — see the "Needed" line below.
- [x] Canvas2D `getImageData`/`putImageData` JS wiring (2026-09-16) — `render::Canvas2D::get_image_data` was already real (full-texture GPU readback); this pass adds `Canvas2D::put_image_data(x, y, w, h, rgba)` (`wgpu::Queue::write_texture`, requires the `COPY_DST` texture usage flag added alongside it) and binds both to `js-runtime`'s `canvas_bindings` module. Scope cuts: `getImageData` always returns the whole canvas regardless of the x/y/w/h args passed (no windowed GPU readback); the returned `data` is a real `Uint8Array`, not spec's `Uint8ClampedArray` (no such constructor bound in this crate — same precedent as `crypto.getRandomValues`); `putImageData` only supports the 3-arg form (no `dirtyX/dirtyY/dirtyWidth/dirtyHeight`). `put_image_data` clips correctly against both a negative origin and a region spilling past the canvas edge (tested). Tested at both levels: `render/tests/canvas_test.rs` (4 new tests: direct write, overwrite-not-blend, edge-spill clipping, negative-origin clipping) and `js-runtime/tests/canvas_test.rs` (2 new tests: real drawn-pixel readback, write-then-read-back round trip).
- [x] Canvas2D `strokeRect`/`strokeStyle`/`lineWidth` JS wiring (2026-09-16) — `Canvas2D::stroke_rect(x, y, w, h)` draws a rectangle's outline as four filled bars (one per side), each centered on that edge like real Canvas2D's own stroke positioning, reusing the existing `fill_pipeline`/`draw_rect` machinery (no new shader). Scoped to the one rectangle-outline shortcut real Canvas2D also exposes directly — no general path/`lineTo`/`arc` stroking, no line joins (the four bars simply overlap at each corner, correct for an opaque `strokeStyle` but would double-blend a semi-transparent one). Tested at both levels: `render/tests/canvas_test.rs` (4 new tests: border-only painting, `strokeStyle` vs `fillStyle` independence, `lineWidth` widening, getter round-trips) and `js-runtime/tests/canvas_test.rs` (2 new tests: property round-trip, real drawn-pixel readback through `getImageData`).
- [x] Canvas2D `save`/`restore` JS wiring (2026-09-16) — a real `Vec<CanvasState>` stack on `render::Canvas2D`, `save()` pushes the current `fillStyle`/`strokeStyle`/`lineWidth`, `restore()` pops and re-applies (a no-op on an empty stack, matching real spec). Scoped to just the drawing-state fields this crate actually has — no clip region, transform matrix, or compositing/font state exists here to save/restore. Tested at both levels: `render/tests/canvas_test.rs` (3 new tests: single save/restore round trip, empty-stack no-op, nested LIFO ordering) and `js-runtime/tests/canvas_test.rs` (2 new tests: JS-level round trip, restore-with-nothing-saved doesn't throw).
- [x] Canvas2D `translate` JS wiring (2026-09-16) — `Canvas2D::translate(x, y)` accumulates a plain `(translate_x, translate_y)` offset, applied to every `fillRect`/`clearRect`/`strokeRect` coordinate at the one shared `draw_rect` chokepoint all three funnel through. The one transform this crate supports — no `scale`/`rotate`/`setTransform`/general matrix, since only translation reduces to a plain coordinate offset. Included in `save`/`restore`'s state stack. Tested at both levels: `render/tests/canvas_test.rs` (3 new tests: offset applied, accumulates across calls, undone by `restore`) and `js-runtime/tests/canvas_test.rs` (1 new test: JS-level offset readback via `getImageData`).
- [x] Canvas2D `createLinearGradient`/`addColorStop`/`fillStyle = gradient` JS wiring (2026-09-16) — reuses the same zero-new-shader per-vertex-color-interpolation trick `render::gpu::shader`'s CSS `linear-gradient` background support already validated: each corner of the filled rect gets its own exact blend color (projected onto the gradient line via `gradient_t`), and the GPU's own triangle interpolation fills the interior. Scoped to exactly 2 effective color stops (smallest/largest `addColorStop` offset become start/end; any stop between them is accepted but ignored — real multi-stop interpolation across a rect would need more than 4-corner interpolation to be exact). Gradient coordinates are plain canvas pixel space, unaffected by `ctx.translate()`. Only `fillRect` supports a gradient fill (`clearRect`/`strokeRect` stay solid-color). Included in `save`/`restore`'s state stack. Tested at both levels: `render/tests/canvas_test.rs` (4 new tests: start/end color blend, `set_fill_style` reverting a gradient to solid, `restore` undoing a gradient) and `js-runtime/tests/canvas_test.rs` (2 new tests: real GPU-blended pixel readback via `getImageData`, string `fillStyle` reverting a gradient).
- [x] Canvas2D `drawImage(source, dx, dy)` JS wiring (2026-09-16) — canvas-to-canvas only: `source` must be a `<canvas>` element that already has an active 2D context (registered in `HostState::canvases`), else this silently does nothing. Built entirely from the existing `get_image_data`/`put_image_data` round trip — no new `render::Canvas2D` API needed. Scoped to the 3-arg form only (no `dw`/`dh` scaling overload, no 9-arg source-rectangle overload) and to a `<canvas>` source (no `HTMLImageElement`/`HTMLVideoElement`/`ImageBitmap`/`OffscreenCanvas`). Tested in `js-runtime/tests/canvas_test.rs` (2 new tests: real cross-canvas pixel copy at an offset, no-op when the source has no active 2D context).
- [x] Canvas2D `beginPath`/`moveTo`/`lineTo`/`closePath`/`fill` JS wiring (2026-09-16) — a real filled path via fan triangulation from `path_points[0]` (`submit_vertices` generalized from a fixed 6-vertex rect buffer to an arbitrary triangle-list slice to support this, no new shader). **Exact only for convex polygons** — a concave path paints the wrong region, since there's no general polygon triangulator (ear-clipping or similar) here. `moveTo`/`lineTo` are functionally identical (both just append a point — no subpath-boundary tracking, only one polygon per `beginPath`). No stroking a path (only `strokeRect`'s existing rectangle shortcut), no curves (`arc`/`bezierCurveTo`/`quadraticCurveTo`), no gradient fill for paths (`fillRect`-only, to avoid duplicating gradient-projection logic for arbitrary triangle geometry). The current path isn't part of `save`/`restore`'s state stack, matching real spec. Tested at both levels: `render/tests/canvas_test.rs` (4 new tests: triangle fill, 4-point square fill, <3-point no-op, `beginPath` discarding prior points) and `js-runtime/tests/canvas_test.rs` (2 new tests: real triangle-fill pixel readback via `getImageData`, <3-point no-op).
- [x] Canvas2D `fillText(text, x, y)` JS wiring (2026-09-16) — real shaping/rasterization via `layout_engine::layout_text` (`cosmic-text`+`swash`, the same pipeline page text already uses) and `render::text::composite_glyphs` (the same CPU alpha-blend compositor page text already uses) — not a stub. Built as a full-canvas `get_image_data`/`composite_glyphs`/`put_image_data` round trip, no new GPU pipeline. Scope cuts: no `ctx.font` yet (every call uses a fixed 16px generic-sans-serif — real spec's own default is `"10px sans-serif"`); no text wrapping (the `maxWidth` 4th argument isn't accepted); `y` behaves like `textBaseline = "top"` (measured from the text's own top), not the default `"alphabetic"` baseline, since this reuses `layout_text`'s glyphs exactly as `layout_engine`'s own page-text pipeline positions them, with no separate baseline-offset math added; no `strokeText`/`measureText`/gradient fill. Tested at both levels: `render/tests/canvas_test.rs` (2 new tests: non-background pixels painted, empty string is a no-op) and `js-runtime/tests/canvas_test.rs` (2 new tests: real drawn-pixel readback via `getImageData`, empty string paints nothing).

- [x] Canvas2D `toDataURL()` JS wiring (2026-09-16) — real PNG encoding via a new `image_decode::encode_png` (the reverse direction of that crate's existing `decode`, same `image` crate dependency) plus `base64`, producing a genuine `data:image/png;base64,...` URL a page could actually decode. On `HTMLCanvasElement` itself (real spec placement, not `CanvasRenderingContext2D`). Scope cuts: always PNG regardless of the requested MIME type (no JPEG/WebP *encoder* wired); requires `getContext('2d')` to have already been called on the element (returns `""` otherwise, real spec would still produce a blank-image data URL); no `toBlob` (no `Blob`/async-callback machinery in this crate's JS bindings). Tested at both levels: `render/tests/canvas_test.rs` (1 new test: base64-decode + `image_decode::decode` round trip confirms real, correct PNG bytes) and `js-runtime/tests/canvas_test.rs` (2 new tests: real data-URL prefix after drawing, empty string with no active context).
- [x] Canvas2D `ctx.font`/`fillText`/`strokeText`/`measureText` JS wiring (2026-09-16) — real `ctx.font` parsing (`"<size>px <family>"`, one generic keyword or a named-plus-generic pair, mirroring `layout_engine::FontFamily::named`'s own shape — no weight/style/line-height/multi-family-list), stored as real state (`font_size`/`font_family`) included in `save`/`restore`. `measureText(text).width` reuses the exact same `layout_engine::layout_text` shaping `fillText` calls, at the current font — only `width`, no other `TextMetrics` fields. `strokeText` **is not a real outline stroke** — this crate only has alpha-coverage glyph bitmaps to fill, not glyph-outline path data to trace, so it paints the same glyphs solid in `strokeStyle` instead (genuinely different from spec at any size/lineWidth where the distinction would be visible — documented, not silently wrong). Tested at both levels: `render/tests/canvas_test.rs` (7 new tests: font getter/setter round-trip incl. named family, invalid-string no-op, `measureText` positive-width and font-size-scaling, `strokeText` uses `strokeStyle` not `fillStyle`, font included in save/restore) and `js-runtime/tests/canvas_test.rs` (3 new tests: JS-level `font` round trip, `measureText` object shape, `strokeText` color readback via `getImageData`).
- [x] Canvas2D `createRadialGradient` JS wiring (2026-09-16) — a genuinely exact, real per-pixel circular gradient, not an approximation: unlike the linear case (which reuses the solid-color pipeline's 4-corner-color-interpolation trick, exact only because a linear function is affine), a radial gradient's `t = distance/radius` is *not* affine in screen position, so this gets its own dedicated GPU pipeline/shader (`radial_pipeline`/`RadialVertex`/`RADIAL_SHADER_SRC`) — `local_pos` (position relative to the gradient center) is itself affine and interpolates exactly across the rect, and the nonlinear `length(local_pos) / radius` clamp-and-lerp happens per-fragment in `fs_main`. Scoped to a single circle: only the outer circle (`x1`, `y1`, `r1`) from `createRadialGradient(x0, y0, r0, x1, y1, r1)` is used, real spec's two-circle cone-gradient shape isn't modeled. `render::Canvas2D::fill_gradient` is now a `FillGradient` enum (`Linear`/`Radial`) rather than a bare `LinearGradient`, included in `save`/`restore`. Tested at both levels: `render/tests/canvas_test.rs` (4 new tests: center/edge color blend, a true-circle-not-diamond regression guard confirming the per-pixel-shader approach over a naive corner-interpolation one, `fill_gradient()` accepting both variants) and `js-runtime/tests/canvas_test.rs` (1 new test: real center/corner pixel readback via `getImageData`).

- [ ] **OffscreenCanvas/WebGL — deferred, not abandoned (revised 2026-09-16).** Originally recorded as a deliberate non-goal the same day (see git history for the superseded reasoning); explicitly reopened by the user as real future work, to be picked up only after every other item in this matrix and the rest of `spec/` is finished, and gated on a deep dedicated spec pass first (this one-paragraph note is not that spec). Why it's last, not abandoned: WebGL means a full separate spec on top of `render::gpu`'s existing `wgpu` pipeline (shader compilation/validation - GLSL ES, a huge distinct API surface: buffers, textures, framebuffers, extensions) - not a natural extension of Canvas2D's small set of real 2D primitives this matrix already tracks. OffscreenCanvas needs `Canvas2D` (which owns a `wgpu::Device`/`Queue`, and is looked up DOM-node-keyed via `HostState::canvases`) to become constructible with no DOM node and transferable across `workers`' real OS threads (`transferControlToOffscreen()`) - a structural redesign, not an incremental addition. Concrete motivating case discussed: YouTube's main feed (plain `<video>` playback) doesn't need either, but its VR/360° video mode does (WebGL-projected video sphere) - a real, named gap for a real target page, not a hypothetical. Before implementation starts: write the deep spec this note explicitly is not (scope cut choices, which `wgpu` primitives back which WebGL calls, the OffscreenCanvas/worker threading model, a concrete test plan) as its own `spec/` document.
